# GGA — chargement des fichiers et overlays de code

Mesuré le 2026-10-19 (session 2, Opus) en lisant `build/main.dis.txt` et le désassemblage des fichiers de code décompressés.
« Index » = numéro de fichier **du jeu**, qui commence à 1. **Index du jeu = index de `config/rommy.json` + 1** (le fichier 8 de rommy est le fichier 9 du jeu).

## Tables en RAM (code principal, mesuré)
- `0x8002BB94` : table Nisitenma-Ichigo (offset ROM du fichier `idx` = `entrée[idx-1] & 0x7FFFFFFF`, bit 31 = compressé). Indices valides : 1..0xA10 (test `sltiu 0xa11`).
- `0x80026B00` : **table des adresses de chargement**, 8 octets par fichier : `{début, fin}` (entrée `idx-1`). Fin − début = taille en mémoire, BSS comprise.
  Pour les fichiers de code, `début` est l'adresse RAM (VRAM). Pour les données, c'est une adresse segmentée (`0x01..0x0B` dans l'octet haut) ou 0.
- `0x80026720` : paires `u16` {premier index, numéro de segment} : plages de fichiers → segment (sert aux relocations / pointeurs segmentés des données, à creuser).

## Fonctions du chargeur (mesuré ; noms donnés par nous)
| RAM | Rôle |
|---|---|
| `0x80003E50` | `file_load(idx, dest)` : lit l'entrée, choisit brut / compressé, puis vide les caches (`0x80012150`, `0x8001AD00`, `0x8001AC80`, supposé : writeback D-cache / invalidation I-cache) et met à zéro la BSS jusqu'à `dest + (fin − début)`. Renvoie la fin. |
| `0x80001CF8` | lecture brute ROM → RAM (supposé : enveloppe de `osPiStartDma`, non vérifié). |
| `0x80002F40` | lecture + décompression en flux. En-tête de 4 octets : bit 31 = 1 → **zlib** (`0x800035D8`) ; bit 31 = 0 et 4 bits hauts = 0 → **LZKN64** (même format que Goemon 1, valeur = taille compressée en-tête compris) ; 4 bits hauts ≠ 0 → variante LZKN64 en plusieurs morceaux (pas encore vue dans un fichier). |
| `0x80003A8C` | `file_load_at(idx, dest)` par la file d'attente (`0x8000397C` / `0x80003B28`, 8 listes `{idx|drapeaux, dest}`, bit `0x40000000` = dernière entrée ; dest 0 = allocation, −1 = tas aligné). |
| `0x800047EC` | **`overlay_load(idx)`** : charge le fichier à `début` de la table `0x80026B00`, appelle `0x800079F4(idx)`, plante volontairement si la taille ≥ `0x47001`. Appelé depuis le fichier 6 (ex. `0x800C7BAC` avec idx 8). |

## Modules TLB à `0x08000000` (mesuré le 2026-10-19, étape 3)
En plus des 4 fichiers ci-dessus, **311 modules de code** sont liés à l'adresse virtuelle `0x08000000` (table `0x80026B00` : début = `0x08000000`).
- **Liste** : fichiers du jeu **16..312 et 314..327** (rommy 15..311 et 313..326 ; le 313 est vide). Liste complète avec tailles : `build/seg8_modules.txt` (colonnes : idx jeu, idx rommy, taille en mémoire, taille décompressée ; 20 ont une BSS). Critère : au moins un `jr $ra` dans le fichier (heuristique ; la liste forme deux plages continues, ce qui la rend crédible). Certains commencent par des zéros (ex. 323, 327) : le point d'entrée n'est pas forcément au début.
- Autres fichiers liés à `0x08000000` mais **sans code** (données mappées de la même façon) : 11..15 (bruts) et 328..411.
- Table des types `0x80026720` (paires `u16` {limite, type}, 248 entrées) : fichiers 2..0x19B (2..411) = type `0x11` ; pour ce type le chargeur aligne l'adresse sur 4 Ko (`0x800045D4` → `0x40000000`) : c'est la condition du mappage TLB.
- **Mécanisme** (comme Goemon 1, voir `../Goemon64Recomp/patches/functions.h` : `file_map_tlb_overlay`) :
  - le module est chargé dans le tas à une adresse physique alignée sur 4 Ko (pas de relocation à la copie) ;
  - `0x80004638` = `module_map(idx)` (idx < 0x01000000, sinon c'est une adresse directe) : retrouve l'adresse physique (`0x8000455C`), puis appelle **`osMapTLB` (`0x8000FC90`)** pour chaque paire de pages de 4 Ko (entrées de 8 Ko, virtuel `0x08000000 + n*0x2000`), au plus 31 entrées (0x3E000 octets ; plus gros module mesuré : 0x1C3E0). Le module en cours est mémorisé (`0x800379AC` / `0x800379B0`) ; `0x8000462C` le renvoie ; `0x800047C8` → `0x8001A9A0` (supposé `osUnmapTLBAll`) au changement de scène.
  - **un seul module mappé à la fois** ; l'appelant fait ensuite `jalr` vers un point d'entrée `0x08xxxxxx` (ex. `0x800DB76C` → `0x800DB77C`) ;
  - pour lire les données d'un module sans le mapper : `0x8000458C(idx, adr_0x08)` = adresse physique + (adr & 0xFFFFFF).
- Exemple de description de scène (fichier 6, `0x800DAE08`) : `+0x82` = overlay (9), `+0x94` = module (0x15 = 21), `+0x8C` = point d'entrée `0x0800390C`.
- Dans les modules : `jal` internes vers `0x08xxxxxx`, accès au moteur en absolu (`lui 0x800D`, `0x8017`… = code principal, fichier 6 et overlay).

## Conséquences pour la recomp
- `ga.toml` : code principal + fichier 6 en sections fixes ; fichiers 8 / 9 / 10 en overlays à `0x801738A0` (adresses fixes, pas de relocation).
- **311 modules TLB à `0x08000000`** : c'est le gros morceau, et c'est le même problème que Goemon 1 (qui a `patches/overlay_relocs.h`, des relocations par fichier, `VMA 0x08000000`). La recomp ne gère pas la TLB : il faudra traiter chaque module comme un overlay à `0x08000000`, savoir lequel est « mappé » (accroche sur `0x80004638`) et traduire les accès `0x08xxxxxx` → adresse physique. Goemon 1 avait une décompilation pour générer ses relocations ; pour GGA il faudra les **calculer** (paires `lui`/`addiu` et `jal` vers `0x08xxxxxx`). Étape 4.
- **Bug de `tools/ga_rommy.py` : CORRIGÉ (2026-10-19)** : le fichier rommy 8 est LZKN64 ; décompresseur en Python pur dans `ga_rommy.py`, 0x44400 octets, identique à la bibliothèque `lzkn64`. Les 4 fichiers de code sont extraits par `.\tools\disasm_code.ps1` (`build/code_<idx rommy>_<VRAM>.bin` et `.dis.txt`, tailles vérifiées contre le tableau ci-dessus).
- Pour charger le bon overlay à l'exécution, la recomp doit savoir quel fichier est chargé : point d'accroche naturel = `0x800047EC` / `0x80003E50` (à comparer avec `../Goemon64Recomp/patches/overlay_reloc.c`).

## Comment Goemon 1 fait tourner ses modules TLB (lu dans `../Goemon64Recomp`, 2026-10-19, étape 4)
1. **Symboles et relocations** : la décompilation `lib/mnsg` (splat, `config/usa/splat.yaml`) décrit chaque module comme un segment `type: code`, `vram: 0x8000000`, `overlay: yes`, `exclusive_ram_id: tlb_overlay`. Le lien se fait avec `ld --emit-relocs` → `mnsg.elf` garde les relocations.
2. `N64Recomp --dump-context mnsg.dump_context.toml` (entrée `elf_path` + `relocatable_sections_path`) → `Goemon64RecompSyms/mnsg.syms.toml` : un `[[section]]` par module (`rom`, `vram = 0x08000000`, `size`, `relocs = [{type = "R_MIPS_HI16"/"LO16"/"26", vram, target_vram}]`) + les fonctions.
3. `mnsg.toml` : `symbols_file_path` = ce syms.toml, `relocatable_sections_path = "mnsg.overlays.txt"` (une ligne par module, `.file_24`…). Pour ces sections, N64Recomp génère du code qui calcule les adresses internes à partir de l'adresse où la section a été chargée → plus besoin de TLB.
4. Patchs (`patches/required.c`) :
   - le chargeur de fichiers (`func_80001C00`, équivalent de notre `0x80003E50`) appelle `recomp_load_overlays(rom, buf, size)` (le runtime sait alors quelle section est à quelle adresse physique), puis `overlay_apply_relocations` (`overlay_reloc.c` + `overlay_relocs.h` généré depuis l'ELF) qui corrige les **pointeurs 32 bits dans les données** (`R_MIPS_32`), seuls non traités par N64Recomp ;
   - le moteur appelle des fonctions de modules par pointeur `0x08xxxxxx` (tâches) : patch qui traduit ces pointeurs en adresse physique (`ptr − 0x08000000 + début du module`) ; idem pour le seul autre appel direct.
5. ROM : la recomp est générée à partir de la ROM **décompressée**. Le joueur fournit la ROM d'origine, que le jeu décompresse au premier lancement (`src/game/rom_decompression.cpp`, `.decompression_routine` dans `main.cpp`). Le résultat doit être identique à la ROM qui a servi à la recomp (CRC écrits dans l'en-tête).
